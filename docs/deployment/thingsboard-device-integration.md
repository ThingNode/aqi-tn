# ThingsBoard Device Integration Spec (for hardware/firmware implementation)

**Purpose:** This document specifies exactly how the existing simulator talks to
ThingsBoard, so that real sensor hardware can be brought up as a drop-in
replacement — publishing to the **same ThingsBoard devices**, the **same topic**,
the **same JSON shape**, and the **same telemetry keys** the rest of the system
(API bridge, calibration, AQI calculation, web app) already depends on.

Everything below is taken directly from the current, working implementation
(not from planning docs). Where the codebase diverges from the original
product-spec design doc, the code (i.e. this document) is the ground truth.

---

## 1. Target ThingsBoard instance

| Item | Value |
|---|---|
| Base URL | `https://demo.thingsnode.cc` |
| MQTT host | `demo.thingsnode.cc` |
| MQTT port | `1883` (plaintext) by default. **TLS port 8883 has not yet been confirmed as open on this instance — verify with the ThingsBoard tenant admin before hardware rollout.** |
| WebSocket telemetry endpoint (server-side only, not for devices) | `wss://demo.thingsnode.cc/api/ws/plugins/telemetry` |

There is no CoAP or HTTP telemetry transport in use — **MQTT only** for device → platform.

A local/offline ThingsBoard instance (`thingsboard/tb-postgres:3.9.1`, HTTP `8080`,
MQTT `1883`) is available for dev/test via `infra/docker-compose.yml`
(`local-thingsboard` compose profile), but production/demo devices point at the
hosted instance above.

## 2. Device identity & provisioning

### 2.1 One ThingsBoard device per station, name = station ID

Every physical sensor station corresponds to exactly one ThingsBoard device.
**The ThingsBoard device `name` must exactly equal the station `id`** from the
station registry (`config/stations.yaml`) — this is how the backend matches
ThingsBoard devices back to station metadata (location, name, site class, etc.).

Device type on all provisioned devices: `"aqi-station"`.

Current 15-station registry (`config/stations.yaml`), i.e. the 15 device names
that already exist in ThingsBoard and that hardware must be matched to one-to-one:

```
sta-ref-battaramulla-01
sta-ref-battaramulla-02
sta-bg-diyawanna
sta-cor-kandy-peliyagoda
sta-cor-negombo-wattala
sta-cor-galle-bambalapitiya
sta-cor-hlr-nugegoda
sta-cor-baseline-borella
sta-sch-peliyagoda
sta-sch-wattala
sta-sch-bambalapitiya
sta-sch-nugegoda
sta-ind-port
sta-ind-kelaniya
sta-coast-galle-face
```

Each has associated metadata (display name, lat/lng, site class, corridor,
district) in `config/stations.yaml` — this metadata lives **only** in that YAML
file / the app's own `/api/v1/stations` endpoint, **not** in ThingsBoard. There
is nothing for firmware to read or write there.

### 2.2 Device credentials: per-device MQTT access token

Authentication is ThingsBoard's standard **MQTT "Access Token"** credential
type (basic single-token auth, not X.509, not username+password, not a shared
secret across devices).

- Each station/device has its **own unique access token**, generated by
  ThingsBoard when the device is created.
- The token is used as the **MQTT username**, with **no password** and no
  client-cert.
- Tokens for the current 15 demo devices exist and are stored (not committed to
  git) in `thingsboard-device-tokens.env`, one line per station, e.g.:
  ```
  TB_TOKEN_STA_BG_DIYAWANNA=<token>
  TB_TOKEN_STA_COAST_GALLE_FACE=<token>
  ```
  Variable naming convention: `TB_TOKEN_` + station ID, uppercased, `-` → `_`
  (see `services/thingsboard/provision.py`, function `normalized()`).
- **Action for the implementation team:** request the real device access
  tokens for each of the 15 station IDs above through a secure channel (do not
  ask for them over chat/email in plaintext). Whoever owns the ThingsBoard
  tenant can also re-provision/rotate them via the existing provisioning script
  (`services/thingsboard/provision.py --create`) if fresh tokens are preferred
  for hardware go-live. **We recommend rotating tokens before hardware
  go-live**, since the current tokens have been used for simulation/testing.
- If a device already exists in ThingsBoard but its access token needs to be
  looked up again: ThingsBoard REST `GET /api/device/{device_id}/credentials`
  returns `{"credentialsType": "ACCESS_TOKEN", "credentialsId": "<token>"}`.

No X.509 mutual-TLS auth and no attribute-based provisioning (e.g. ThingsBoard
device provisioning API / "auto-provisioning") is used anywhere in the current
pipeline — devices are pre-created centrally and tokens are distributed
out-of-band.

## 3. MQTT publish contract (the core of this spec)

### 3.1 Connection

- Protocol: MQTT (v3.1.1/v5, standard ThingsBoard broker), TCP.
- Host/port: see §1.
- **Username:** the device's access token.
- **Password:** none / empty.
- **TLS:** off by default against the current instance (confirm before go-live
  whether the production deployment requires TLS on 8883).
- QoS: **1** (at-least-once) is used by the reference implementation.
- The reference implementation opens a fresh MQTT connection per publish and
  disconnects immediately after each message is acknowledged (it does **not**
  keep a persistent MQTT session). A persistent connection with periodic
  publishes is equally valid on the ThingsBoard side — this is an
  implementation choice, not a protocol requirement. A persistent connection is
  actually **preferable** for real hardware (lower connection overhead, faster
  fault detection via MQTT keepalive/LWT), it's simply not what the Python
  simulator happens to do.

### 3.2 Topic

```
v1/devices/me/telemetry
```

This is ThingsBoard's standard single-device MQTT telemetry topic (the token
used to authenticate the MQTT session implicitly identifies which device the
telemetry belongs to — no device ID is included in the topic or payload).

### 3.3 Payload envelope

```json
{
  "ts": 1735689600000,
  "values": { "...": "..." }
}
```

- `ts`: **required**, Unix epoch **milliseconds**, integer, UTC.
- `values`: flat JSON object (no nesting) containing the telemetry keys below.

### 3.4 Required telemetry keys

This exact key set is what the backend (`apps/api/app/thingsboard_bridge.py`,
`TELEMETRY_KEYS`) subscribes to and what downstream processing
(`apps/api/app/main.py: canonicalize()`) expects. **Use these exact key names**
— they are case-sensitive and unused/renamed keys will silently not reach the
app.

| Key | Type | Unit | Required? | Notes |
|---|---|---|---|---|
| `pm1` | number | µg/m³ | recommended | PM1.0 mass concentration |
| `pm2_5_raw` | number | µg/m³ | **required** | Raw/uncorrected optical PM2.5 reading, **before** any humidity correction. The backend applies its own RH correction server-side — send the raw sensor reading, not a corrected value. |
| `pm10_raw` | number | µg/m³ | **required** | Raw/uncorrected PM10, same rule as above |
| `no2` | number or `null` | ppb (TBD — confirm target unit with the sensor datasheet) | optional | Currently always `null` in simulation (no synthetic NO2 model exists yet). Real hardware with a NO2 sensor should populate this — it's a stated product differentiator. If a station has no NO2 sensor, send `null` explicitly rather than omitting the key. |
| `temperature` | number | °C | recommended | Ambient temperature |
| `humidity` | number | % RH (0–100) | **required** | Used directly in the server-side PM correction formula — must be a plausible RH percentage, not a raw ADC/sensor count |
| `pressure` | number | hPa | recommended | Barometric pressure |
| `wind_speed` | number | m/s | optional | Only relevant for stations with a wind sensor |
| `wind_direction` | number | degrees (0–360, meteorological "wind from" convention) | optional | |
| `precipitation` | number | mm | optional | |
| `battery_v` | number | volts | recommended | Station power-supply/battery voltage, for health monitoring |
| `rssi` | integer | dBm | recommended | Cellular/WiFi/LoRa radio signal strength, for health monitoring |
| `firmware` | string | — | recommended | Firmware version string, e.g. `"aqi-node-1.0.0"`. **Sent as a telemetry (time-series) value, not a ThingsBoard attribute.** |
| `source_type` | string enum | — | **required** | **Must be `"OWN_SENSOR"` for real hardware.** (The simulator sends `"SIMULATED"`; the app uses this field to select provenance/confidence metadata shown to users — sending the wrong value will mislabel real readings as simulated in the UI.) |

Valid values for `source_type` (from `packages/schemas/src/aqi_schemas/models.py`):
`OWN_SENSOR`, `PUBLIC_CEA`, `PUBLIC_NBRO`, `PUBLIC_WAQI`, `PUBLIC_AQIIN`, `SIMULATED`.
**Hardware devices always use `OWN_SENSOR`.**

### 3.5 Server-side validation the payload must satisfy

`apps/api/app/main.py: canonicalize()` requires `pm2_5_raw`, `pm10_raw`, and
`humidity` to be present and numeric — if any is missing or fails to parse as a
float, the **entire reading is silently dropped** from the app's own data
store (though it's still visible in ThingsBoard itself, for diagnostics).

Range check: readings are rejected if `pm2_5_raw > 1000` or `pm10_raw > 2000`
(µg/m³) — treat these as sane upper bounds for firmware-side validation too
(e.g. don't publish clearly-faulty sensor saturation values without clamping
or flagging).

### 3.6 Example payload (reference — matches the shape the simulator sends)

```json
{
  "ts": 1735689600000,
  "values": {
    "pm1": 12.4,
    "pm2_5_raw": 21.8,
    "pm10_raw": 38.6,
    "no2": null,
    "temperature": 29.1,
    "humidity": 78.5,
    "pressure": 1008.3,
    "wind_speed": 2.1,
    "wind_direction": 214.0,
    "precipitation": 0.0,
    "battery_v": 12.6,
    "rssi": -67,
    "firmware": "aqi-node-1.0.0",
    "source_type": "OWN_SENSOR"
  }
}
```

### 3.7 Publish interval

**Every 1–5 minutes per device.** The simulator defaults to 300 seconds (5
minutes); this is also the product's target cadence for real stations. Faster
publishing is not harmful but isn't required. Avoid intervals slower than 5
minutes if the station has connectivity/power to support 5-minute reporting —
downstream dashboards assume roughly this freshness.

---

## 4. Attributes: none required

**ThingsBoard client-side and shared attributes are not used anywhere in this
system.** The backend's WebSocket subscription explicitly requests zero
attributes (`"attrSubCmds": []`). Firmware does **not** need to implement
`v1/devices/me/attributes` publish/subscribe.

All device/station metadata (name, coordinates, site class, district,
operator, expected parameters) is managed centrally in the application's own
`config/stations.yaml` registry, not in ThingsBoard. If firmware needs to
report something like installed firmware version or hardware revision, send it
as a **telemetry** key (as `firmware` already is), not a ThingsBoard attribute
— the backend does not currently read attributes at all.

---

## 5. RPC / remote commands: none implemented

There is currently no RPC channel between ThingsBoard and the application (no
server → device commands, no device → server RPC). If the hardware needs
remote configuration (e.g. change sampling interval, reboot) that is new scope
not currently exercised by any part of this pipeline — flag it separately if
required, since the backend would need new code to issue such commands.

---

## 6. What the implementation team does NOT need to build

To be explicit about scope, since ThingsBoard deployments often include more
than this project uses:

- No ThingsBoard rule chains, no dashboards, no alarms are used by the
  application — all calibration, AQI index calculation, and provenance
  handling happen in the application's own API, not in ThingsBoard.
- No ThingsBoard attribute publish/subscribe.
- No RPC.
- No X.509 client certs.
- No multi-tenant / customer hierarchy handling in ThingsBoard (tenant ID is
  an optional, currently-unused config value on the application side).

The device firmware's job is narrowly: **connect over MQTT with the
per-device access token, and publish the JSON payload in §3 to
`v1/devices/me/telemetry` every 1–5 minutes.** Everything else (calibration,
AQI math, storage, web dashboard) is already implemented and consumes exactly
that telemetry stream.

## 7. Handoff checklist

- [ ] Confirm with ThingsBoard tenant admin whether MQTT should use plaintext
      `1883` or TLS `8883` for production hardware, and get the answer into
      firmware config.
- [ ] Obtain (or have the tenant admin regenerate) per-device MQTT access
      tokens for the 15 station IDs listed in §2.1, delivered over a secure
      channel — not plaintext chat/email.
- [ ] Confirm each physical unit is flashed with the token matching its
      intended station ID (a token mismatch would silently attribute one
      station's data to a different station's dashboard entry).
- [ ] Implement the exact payload shape in §3.3–§3.6, using `source_type:
      "OWN_SENSOR"`.
- [ ] Verify `pm2_5_raw`, `pm10_raw`, and `humidity` are always present and
      numeric (see §3.5) — missing/malformed values cause silent data loss on
      the backend.
- [ ] Confirm publish cadence of 1–5 minutes per device.
- [ ] After first hardware bring-up, verify data end-to-end: check the raw
      values arrive in ThingsBoard's "Latest telemetry" for the device, then
      confirm the value shows up in the application (`/api/v1/readings/latest`
      or the web dashboard) — a value present in ThingsBoard but absent from
      the app indicates a validation/key-name mismatch per §3.5.
